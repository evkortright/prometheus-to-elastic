# Module 1 Cheat Sheet: PromQL Inside ES|QL
## Adapted for OTel Astronomy Shop — Real Data

**Data stream:** `metrics-generic.prometheus-default`
**Time range:** Use "Last 15 minutes" for live demos, or pin a fixed window for recording
**Sanity check before going live:**
```esql
FROM metrics-generic.prometheus-default
| KEEP @timestamp, __name__, service_name
| SORT @timestamp DESC
| LIMIT 5
```
Expected: rows with timestamps within the last few minutes.

---

## The core demo metric

`traces_span_metrics_calls_total` — span-derived request counter covering all 19 services.
This is generated by the OTel Collector's span metrics connector, not by Prometheus scraping.
It is the richest metric for the migration story because every service appears.

Key dimensions: `service_name`, `span_name`, `span_kind`, `status_code`

---

## Query 1 — Familiar PromQL
*Run in chart mode in Discover — this is the "nothing changed" moment.
Filter to core application services for a clean, uncluttered chart.*

```esql
PROMQL index=metrics-generic.prometheus-default
  request_rate=(sum by (service_name) (rate(traces_span_metrics_calls_total[5m])))
| WHERE service_name IN ("frontend", "checkout", "cart", "payment", "shipping", "recommendation")
```

**Kibana settings:** Time picker set to **Last 30 minutes** — keeps the post-restart ramp off-screen.

**Expected results (approximate, live traffic):**
- `frontend` — ~14–17 req/s (dominant line)
- `cart` — ~2–3 req/s
- `checkout`, `shipping`, `payment`, `recommendation` — ~0.1–1 req/s

**What to say:** "This is the exact same PromQL you'd run in Grafana. I didn't change the syntax. I just changed where it runs."

---

## Query 2 — Add ES|QL power
*Shows PromQL as the entry point, ES|QL pipeline as the exit — the migration payoff.
Switch to table view for this one.*

```esql
PROMQL index=metrics-generic.prometheus-default
  request_rate=(sum by (service_name) (rate(traces_span_metrics_calls_total[5m])))
| WHERE service_name IN ("frontend", "checkout", "cart", "payment", "shipping", "recommendation")
| STATS max_rate = MAX(request_rate) BY service_name
| SORT max_rate DESC
```

**Expected result:** 6 groups, one per service, sorted by peak rate:
- `frontend` — ~17 req/s
- `cart` — ~3.5 req/s
- `recommendation` — ~1.5 req/s
- `checkout` — ~1.2 req/s
- `shipping` — ~0.4 req/s
- `payment` — ~0.2 req/s

**What to say:** "The PROMQL block is unchanged. The pipes after it are ES|QL. I started with a
Prometheus rate query, then asked: give me the peak rate per service, sorted highest to lowest.
One query. No dashboard. No separate tool. In pure PromQL you'd need topk() for something like
this — and you still couldn't get a clean ranked table. Here it's just a pipe."

## Query 3 — Payment service error rate (Scene 5)
*Use label selectors inside PromQL curly braces — this is the only form that renders
as a chart in Kibana Discover for this metric. Pipes after PROMQL break chart rendering
when grouping by multiple dimensions.*

```esql
PROMQL index=metrics-generic.prometheus-default
  error_rate=(sum(rate(traces_span_metrics_calls_total{status_code="STATUS_CODE_ERROR", service_name="payment"}[5m])))
```

**Kibana settings:** Last 30 minutes, chart view.

**What you'll see before flag toggle:**
- Organic error pattern at ~0.004 req/s — humped shape, ~5 min on / ~5 min off
- This is the load generator hitting a payment edge case naturally

**What you'll see after `paymentFailure` set to 25%:**
- Spike to ~0.04–0.06 req/s — approximately 10x the organic baseline
- Appears ~3–4 minutes after flag toggle
- Drains back to baseline ~5 minutes after flag turned off

**What to say:**
- Before: "The payment service already has an organic error pattern. See these humps?
  In Grafana this would need a separate panel. Here I just changed the metric selector."
- After spike: "That's a 10x increase — visible automatically because Prometheus is
  remote_writing everything it sees."

**Note:** Do NOT use `sum by (service_name, status_code)` with a WHERE pipe for this scene —
it breaks chart rendering in Kibana Discover. Use label selectors in curly braces instead.

## Query 4 (Capstone) — LOOKUP JOIN
*The Module 4 preview — shows what becomes possible in Elastic that was never possible in Prometheus.*

> ⚠️ Requires `service_catalog` lookup index to be created first. Do not run live in Module 1
> unless the index exists. Save this for Module 4.

```esql
PROMQL index=metrics-generic.prometheus-default
  request_rate=(sum by (service_name) (rate(traces_span_metrics_calls_total[5m])))
| LOOKUP JOIN service_catalog ON service_name
| SORT request_rate DESC
```

## Side-by-side comparison (the Module 1 money shot)

**In Prometheus** (`http://localhost:9090`):
```promql
sum by (service_name) (rate(traces_span_metrics_calls_total[5m]))
```
→ 19 result series, instant vector

**In Elastic Kibana** (Discover → ES|QL):
```esql
PROMQL index=metrics-generic.prometheus-default
  request_rate=(sum by (service_name) (rate(traces_span_metrics_calls_total[5m])))
```
→ Same 19 services, time-series chart, table view, pipeable

**What to say:** "Same metric. Same PromQL. One is your existing Prometheus stack — I didn't touch it.
The other is Elastic, receiving the same data via a single remote_write block.
Your team doesn't need to relearn anything on day one."

## Bonus — ES|QL native equivalent
*Only show if asked "can I do this without PromQL?" — demonstrates the underlying TSDB.*

```esql
FROM metrics-generic.prometheus-default
| WHERE __name__ == "traces_span_metrics_calls_total"
| WHERE @timestamp > NOW() - 15 MINUTES
| STATS COUNT(*) BY service_name
| SORT `COUNT(*)` DESC
```

Note: This is a document count, not a rate — it's a simplified equivalent for illustration only.
The PromQL `rate()` form is the correct way to compute per-second rates.

## Recording notes

- Pin the Kibana time picker to a **fixed window** before recording — live "last 15 minutes"
  will drift mid-demo and change your numbers.
- The chart mode in Discover is the most visually compelling — switch to it before showing Query 1.
- Have Prometheus open in a second tab pre-loaded with the same query — tab switch is the reveal.
- `flagd` traffic is from the feature flag service polling — explain it's infrastructure, not user traffic,
  if anyone asks why it has high req/s.
- `load-generator` appears as a service because it emits its own spans — good to mention as it
  shows the breadth of OTel instrumentation.
- Status codes are OTel format (`STATUS_CODE_ERROR`, `STATUS_CODE_OK`, `STATUS_CODE_UNSET`) —
  not HTTP status codes. Explain this if doing Query 3.
